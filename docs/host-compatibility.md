# USB host compatibility and manifest transport

**The bundled UnifiedHost utility is not qualified for this hardened updater.** Its inspected PIC32 erase command carries no image length/CRC manifest, and its checksum class does not match the generated CRC command. The working SW1 diagnostic firmware still has no update commands. Do not use the stock utility to erase/program this board yet.

Reviewed: **2026-10-14**. Inspection was offline: JAR class/packet processing and repository sources, with no HID device connection. This establishes specific packet facts, not an exhaustive Java/UI review or claim that every UnifiedHost mode is broken.

## Packet observations

The UI's `BootloadUSBDFUFED32bit` creates the PIC32 USB command classes in I2CBootloaderHost. Class bytecode/packet-processor invocation showed:

| Function | Inspected request | Compatibility observation |
|---|---|---|
| Read info/version | command 1, no payload | Existing CRC16/SOH/DLE/EOT frame decodes in our validator. |
| Erase | command 2, **null dataPayload**, 64-byte report allocation | No declared image length or CRC32 is available before erasing. Cannot start our manifest-required session safely unchanged. |
| Program | command 3 with stored HEX chunks | Frame/HEX model assumes payload escaping before packing. Exact HEX ordering/session behavior still needs verification. |
| Checksum | inspected `CommandChecksumUSBMCU32` sets **command 8**, eight-byte payload | Generated USB HID source handles READ_CRC as **command 4** and expects address/length. That class's payload/semantics are not our manifest protocol. UI execution/option usage was not fully traced. |
| Reset/jump | command 5, no payload | Frame decodes, but our safe startup/image-acceptance policy must gate any reset/handoff. Not enabled now. |

The common CRC16 helper matches polynomial 0x1021/initial zero. The host also escapes some byte 0x03 CRC values, although the generated receiver treats DLE generically. Our new strict reserved-escape set currently accepts only 0x01/0x04/0x10; broader host escaping would need an explicit tested compatibility decision.

Concrete read-info/erase/reset packets were generated by the vendor packet processors without contacting hardware:

```text
read-info: 01 10 01 21 10 10 04
     erase: 01 02 42 20 04
     reset: 01 05 A5 50 04
```

They decode with our framing layer. `tests/vendor_host_vectors_test.c` preserves these vectors and confirms the bare erase has no manifest. It also confirms command 8 is unsupported by the current validator. Synthetic unescaped checksum payloads fail framing; that probe demonstrates the packet processor's pre-escaped-model assumption, not a claim that the UI normally supplies an unescaped payload.

The repository's separate `tools/btl_host.py` is **serial-based**, using guard/unlock/data/verify commands A0–A6. It is not this PIC32 USB HID AN1388-style transport and should not be substituted just because it is in the same package.

## Recommended project host

Use a **small project-specific host tool**, retaining HID 64-byte reports and existing CRC16 frame delimiters, with explicit length/CRC32 manifest and verified completion/error responses. This is a recommendation and protocol design work still to implement, not a working uploader delivered here.

Proposed extension contract:

- Negotiate a distinct protocol/version/capability before any destructive command; do not let an old host silently start an update.
- Add an explicit **BEGIN_IMAGE** request carrying fixed origin, declared length and CRC32; validate all fields before invalidating metadata or erasing application pages.
- Keep PROGRAM_HEX only after a successful begin/erase-ready response, acknowledge only when staged rows are written/read-verified, and respond distinctly on rejected record/range/flash failure.
- Commit on verified EOF/image completion; expose STATUS/ABORT for bounded polling and cable-loss recovery. Define retry/idempotence so a lost response cannot cause an accidental duplicate row write.
- Gate reset/run on stored-image validation; no arbitrary memory read/write or config programming commands.
- Host calculates the CRC32 over the filtered/relocated application span, filling gaps with 0xFF and excluding metadata/boot/configuration regions. The current standalone application is not yet that image.

Command IDs, packet schemas, response statuses, compatibility/version negotiation and actual HID library are **not yet selected or implemented**. Next implement/test host image preprocessing and wire schema before binding target operations. A read-only host info/status probe can precede any upload mode.
